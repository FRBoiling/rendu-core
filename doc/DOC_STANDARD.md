# RenduCore 文档编写规范

## 一、文档分类

### 1.1 阶段文档（doc_phase_*.md）
用于记录各开发阶段的设计、实现和进度。

**命名规则**: `doc_phase[序号]_[阶段名称].md`

**文件头格式**:
```markdown
# 阶段 [序号]: [阶段名称]

**状态**: [✅已完成/🚧进行中/⏳待开始] ([百分比]%)
**优先级**: [P0/P1/P2/P3]
**预计工期**: [X-Y] 天
**开始日期**: YYYY-MM-DD
**完成日期**: [已完成日期/待定]
```

### 1.2 技术改进文档（*_improvements.md）
用于记录具体组件的改进方案和实施过程。

**命名规则**: `[组件名]_improvements.md`

**文件头格式**:
```markdown
# [组件名] 改进方案

**状态**: [✅已完成/🚧进行中/⏳待开始]
**创建日期**: YYYY-MM-DD
**最后更新**: YYYY-MM-DD
**负责人**: [姓名]
```

### 1.3 重构文档（*_refactoring.md）
用于记录代码重构的过程和结果。

**命名规则**: `[组件名]_refactoring.md`

**文件头格式**:
```markdown
# [组件名] 重构总结

**重构日期**: YYYY-MM-DD
**重构原因**: [简要说明]
**影响范围**: [影响的模块/文件]
```

### 1.4 专题文档（*_guide.md, *.md）
用于特定主题的详细说明。

**文件头格式**:
```markdown
# [文档标题]

**文档类型**: [指南/参考/手册]
**适用范围**: [模块/系统]
**最后更新**: YYYY-MM-DD
```

## 二、文档结构规范

### 2.1 标准章节顺序

```markdown
# 标题

[文件头元数据]

---

## 一、概述/目标/简介

[简要说明文档的目的和范围]

---

## 二、主要内容/实现方案

[详细描述设计、实现或改进内容]

---

## 三、验收标准/测试验证

[列出具体的验收标准或测试方法]

---

## 四、依赖关系

[说明与其他模块或阶段的依赖]

---

## 五、风险评估/注意事项

[列出潜在风险和注意事项]

---

## 六、进度跟踪/总结

[记录实施进度或总结]

---

## 七、备注

[补充说明、参考资料等]

---

**文档版本**: v[X.X]
**最后更新**: YYYY-MM-DD
```

### 2.2 章节编号规范

- 使用中文数字：一、二、三、...
- 子章节使用：1.1、1.2、... 或 ###、####、...
- 最大层级不超过四级

---

## 三、Markdown 格式规范

### 3.1 标题层级

```markdown
# 一级标题（仅用于文档标题）
## 二级标题（主要章节）
### 三级标题（子章节）
#### 四级标题（细节说明）
```

### 3.2 列表规范

**无序列表**（用于并列项）:
```markdown
- 项1
- 项2
  - 子项2.1
  - 子项2.2
```

**有序列表**（用于有顺序的内容）:
```markdown
1. 第一步
2. 第二步
3. 第三步
```

**任务列表**（用于进度跟踪）:
```markdown
- [x] 已完成任务
- [ ] 未完成任务
- [~] 进行中任务
```

### 3.3 表格规范

```markdown
| 列1 | 列2 | 列3 |
|-----|-----|-----|
| 数据1 | 数据2 | 数据3 |
```

**表格要求**:
- 使用标准 Markdown 表格格式
- 表头居中对齐或左对齐
- 数值列右对齐更佳
- 使用表格进行对比时，应有"改进"列

### 3.4 代码块规范

**语法高亮**（必须指定语言）:
````markdown
```cpp
// C++ 代码
#include <iostream>

int main() {
    return 0;
}
```
````

**内联代码**（使用反引号）:
```markdown
使用 `MessageRouter` 类来路由消息。
```

**代码注释要求**:
- 公开 API 必须有 Doxygen 注释
- 复杂逻辑必须有中文注释
- 注释说明"为什么"而非"是什么"

---

## 四、内容规范

### 4.1 语言风格

- 使用简体中文
- 技术术语保留英文（如 Actor、Router、Metrics）
- 专业名词首次出现时加中文注释
- 避免口语化表达

### 4.2 状态标识

使用 emoji 标识任务状态：

| 符号 | 含义 | 适用场景 |
|------|------|---------|
| ✅ | 已完成 | 功能已实现、测试通过 |
| 🚧 | 进行中 | 正在开发、部分完成 |
| ⏳ | 待开始 | 计划中、尚未开始 |
| ⚠️ | 警告 | 已知问题、需要关注 |
| ❌ | 已取消 | 不再实现的功能 |

### 4.3 文件路径

- 使用相对路径：`src/core/include/core/actor/message_router.h`
- 路径用反引号包裹：`src/core/include/core/actor/message_router.h`
- 跨平台路径统一使用 `/` 分隔符

### 4.4 引用规范

**代码引用**:
```markdown
引用文件 `message_router.cpp` 的第 42-56 行：
```cpp
42|bool MessageRouter::add_route(...) {
43|    // ...
56|}
```
```

**文档引用**:
```markdown
详见 [阶段 18: 高级特性](doc_phase18_advanced.md)。
```

## 五、命名规范

### 5.1 文件命名

| 文档类型 | 命名模式 | 示例 |
|---------|---------|------|
| 阶段文档 | `doc_phase[X]_[名称].md` | `doc_phase18_advanced.md` |
| 改进文档 | `[组件]_improvements.md` | `message_router_improvements.md` |
| 重构文档 | `[组件]_refactoring.md` | `metrics_collector_refactoring.md` |
| 指南文档 | `[主题]_guide.md` | `protobuf_cmake_guide.md` |
| 索引文档 | 大写 + 下划线 | `DOC_INDEX.md` |
| 规范文档 | 大写 + 下划线 | `DOC_STANDARD.md` |

### 5.2 代码命名

在文档中展示代码时，遵循项目的实际命名规范：

```cpp
// 命名空间
BEGIN_NAMESPACE_COMMON
namespace metrics {
}
END_NAMESPACE_COMMON

// 类名
class MessageRouter;
class MetricsCollector;

// 方法名
void add_route();
Result<void> save_state();

// 成员变量（下划线结尾）
bool enable_metrics_;
std::mutex mutex_;
```

## 六、特殊标记规范

### 6.1 优先级标记

```markdown
**优先级**: P0/P1/P2/P3
```

- P0: 阻塞性问题，必须立即解决
- P1: 重要问题，尽快解决
- P2: 一般问题，有时间解决
- P3: 低优先级，可选解决

### 6.2 风险评估表格

```markdown
| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|---------|
| 风险描述 | 高/中/低 | 高/中/低 | 具体措施 |
```

### 6.3 API 文档格式

```cpp
/**
 * @brief 简短描述
 *
 * 详细描述（可选）
 *
 * @param param_name 参数说明
 * @return 返回值说明
 * @throws 异常类型 异常说明
 * @note 注意事项
 * @warning 警告信息
 */
```

## 七、版本控制

### 7.1 文档版本

在文档底部添加版本信息：

```markdown
---

**文档版本**: v1.0
**最后更新**: 2026-02-02
**更新内容**: [简要说明本次更新的内容]
```

### 7.2 变更历史

重要文档应包含变更历史：

```markdown
## 变更历史

| 版本 | 日期 | 作者 | 变更内容 |
|------|------|------|---------|
| v1.0 | 2026-02-01 | boil | 初始版本 |
| v1.1 | 2026-02-02 | boil | 添加测试验证章节 |
```

## 八、文档更新流程

### 8.1 更新时机

- 完成功能开发后更新阶段文档
- 完成改进或重构后创建改进文档
- 修改代码后同步更新相关文档
- 发现问题后记录到"遗留问题"章节

### 8.2 审查机制

- 新增文档需要代码审查
- 重要文档需要技术评审
- 定期检查文档与代码一致性

## 九、常见错误

### ❌ 不规范示例

```markdown
# MessageRouter 测试中断问题

问题分析：测试中断了，因为日志系统有问题。

修复方案：加个锁就好了。

代码如下：
void fix() {
    // 修复代码
}
```

**问题**：
- 缺少文件头元数据
- 章节编号不规范
- 描述过于口语化
- 代码缺少语言标识
- 没有版本信息

### ✅ 规范示例

```markdown
# MessageRouter 测试中断问题 - 改进方案

**状态**: 🚧 进行中
**创建日期**: 2026-02-01
**最后更新**: 2026-02-02

---

## 一、问题概述

Message Router 测试在多线程并发场景下出现中断，根本原因是日志系统与 IoContext 的交互机制设计不合理。

---

## 二、根本原因分析

### 2.1 IoContext 线程安全问题

```cpp
// 原始代码 - 线程不安全
bool IoContext::running() const {
    return running_;  // 非原子读取
}
```

---

## 九、总结

1. ✅ 已识别问题根因
2. 🚧 正在实施修复方案
3. ⏳ 等待测试验证

---

**文档版本**: v1.0
**最后更新**: 2026-02-02
```
